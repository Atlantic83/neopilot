# NeoPilot vs obra/superpowers and mattpocock/skills

> **Status as of 2026-08-17, post-audit.** Waves 1 and 2 fully applied (edits 1–16),
> wave 3 — partially (28–32 and part of 34). Net result for startup context: compression
> saved −5.2 KB, new rules added +4.7 KB, net outcome **−506 bytes (−0.3 %)**.
> The claimed 13–18 % was not reached: it cannot be obtained without touching `3-spec.md`,
> `1-manifest.md`, and `9-memory.md` (43 KB, not read line-by-line during the audit).
> What remains of level 3 — edits 17–27.

Audit dated August 17, 2026. Comparison against two reference frameworks plus a review
of our own instructions along six axes: instruction-following accuracy, token spend,
skillpack size, dashboard reliability, quality loop, developer value.

Method: five parallel subagents (two on the references, three on the per-axis audit); all
key findings re-checked against primary sources by hand. References cloned as of the
audit date: superpowers v6.3.0 (2026-08-12), mattpocock/skills — current main.

Three different bets. mattpocock dropped the process on purpose: "they take away your
control and make bugs in the process hard to resolve" — the orchestrator there is human,
skills are small and composable. superpowers builds discipline without observability: the
agent works for two hours and the user sees one line of narrative. NeoPilot is the only
one trying to take a non-specialist user from words to a working product in a single
dialog — and the price of that bet is the heaviest startup context of the three.

## 1. Instruction-following accuracy and result quality

The loop splits in two, and the halves are built unevenly.

**Traceability — 9/10.** A user requirement cannot disappear: a verbatim-quote manifest,
four gates, blind acceptance against the brief with the specification withheld, the
Manifest axis in review, `placeholder` instead of invented fact. Neither superpowers nor
mattpocock has anything comparable — there the requirement lives in the spec, and the
spec is itself a retelling, i.e. exactly the artifact whose blindness G2/G4 exist to catch.

**Provability — 4/10.** That what was built actually works rests almost entirely on
agent self-reports.

| Hole | Where | What happens in practice |
|---|---|---|
| No red test | [`prompts/executor.md:12`](../skills/neopilot/prompts/executor.md#L12) | "Order: one test — implementation" is a writing order, not red-green. The rule is obeyed when test and code land in one edit |
| No root cause | [`5-repair.md:30`](../skills/neopilot/phases/5-repair.md#L30) | "Fix it so it passes. Touch nothing else" — a direct invitation to treat the symptom |
| Editing the test instead of the code is not forbidden | same place | Weakening an assertion is literal compliance with the follow-up request |
| No floor on test count | [`5-subagents.md:185`](../skills/neopilot/phases/5-subagents.md#L185) | `tail -30` of a suite where "0 tests, exit 0" reads as green |
| Self-review on T0 | [`6-review.md:32`](../skills/neopilot/phases/6-review.md#L32) | "all three axes yourself, inline" — the author reviews their own code, and T0 "is real and it is common" |
| Weakest review on task 01 | [`6-review.md:33`](../skills/neopilot/phases/6-review.md#L33) | The skeleton, schema, and shared primitives get an inline review with no verification of test claims |
| Blocking criteria don't arrive | [`craft-review.md:57`](../skills/neopilot/prompts/craft-review.md#L57) | The list of four always-blocking categories lives in [`6-review.md:131`](../skills/neopilot/phases/6-review.md#L131), which the reviewer never sees. This is exactly the defect the framework itself calls primary: "A rule that lives only in this file does not exist" |
| Contradiction at the last gate | [`8-final.md:51`](../skills/neopilot/phases/8-final.md#L51) vs [`:74`](../skills/neopilot/phases/8-final.md#L74) | "Report it, and fix it if it is small" versus "Never fix one yourself" twenty lines below — and versus rule 5 |

For comparison, superpowers closes this with iron laws: "NO PRODUCTION CODE WITHOUT
A FAILING TEST FIRST. Write code before the test? Delete it. Start over", "Verify RED —
MANDATORY. Never skip", "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST", "If you haven't
run the verification command in this message, you cannot claim it passes".

**Axis 1 verdict: the loop catches a lost requirement far more reliably than work
declared done that wasn't.**

## 2. Token and time spend

### Startup context — 164 KB / ≈ 45,500 tokens before the first line of code

Eleven files are always read: `SKILL.md` (4,850), `0-modes` (2,900), `0-preflight`
(2,380), `0-instruments` (2,970), `0-memory` (1,235), `1-manifest` (3,050), `2-briefing`
(5,900), `3-spec` (5,730), `4-plan` (4,050), `7-instruments` (4,730), `5-subagents` (7,730).

A full T2 run (6 tasks, `semi`, no `polish`): **≈ 71,300 tokens** in the orchestrator's
context, which is never refreshed, plus ≈ 22,300 in subagents.

**The key number is not 71k but 71k × number of turns.** The context is re-read on every
turn; at ~120 turns that's ≈ 8.5M input tokens just on the skill text. It gets cached —
but that's the floor below which a run cannot cost.

### What's already done right

- **`dashboard-template.html` (22,430 tokens) never enters the context** —
  copied with `cp`, with an explicit ban on reading it. This is the framework's main
  optimization, and it's done.
- **Progressive disclosure by phase** — the "unit of loading is a file, not a
  section" rule is correct and is obeyed.
- **Splitting `0-/7-instruments` and `0-/9-memory`** — the right idea: don't drag
  38k characters into an unrefreshable context for questions that arrive four
  phases later.
- **Subagent material kept out of the orchestrator's context** (`executor.md`,
  `craft-review.md` are passed by path) — same solution as superpowers:
  "Hand artifacts over as files".
- **Executor context ceiling in tool calls** — a measured quantity
  (50 calls ≈ 120K, 1,900 tokens per call), with the arithmetic "doubling the ceiling
  doubles the bill". No reference has this.
- **`tools/measure-run.py`** — run measurability. superpowers' evals live in a
  private repository and "are not part of CI today"; mattpocock has no metrics at all.

### Where the overpayment is

**Verbatim duplicates between files** — about 5 KB:

| Repetition | Where |
|---|---|
| "page loads `state.js`… every ten seconds" | `0-instruments:10` ≡ `7-instruments:12` |
| "truth / human view" split | `0-instruments:7-8` ≡ `7-instruments:9-10` |
| "Never put a secret value in here" | `0-instruments:68` ≡ `7-instruments:97` |
| Return contract, 8 lines | `5-subagents:125-133` ≡ `executor.md:67-75` |
| "No more than 25 lines, no code…" | `5-subagents:135` ≡ `executor.md:77` |
| Memory markers block + brownfield | `0-memory:32,61` ≡ `9-memory:20,28,30` |
| Re-review scoped to the fix | `6-review:143-145` ≡ `5-repair:38` |
| "13 repairs across nine tickets, ~40 %" | `6-review:139` ≡ `5-repair:11` |
| "don't open `.neopilot/`" + rationale | `5-subagents:65`, `8-final:19`, `3-spec:202` |

The `0-/7-` and `0-/9-` pairs are a direct consequence of the split: both halves are read
in the same run, so part of the win is eaten back.

**Sections that don't pay for their size:**

| Section | Bytes | Why |
|---|---:|---|
| `7-instruments` "What the dashboard shows" + progress bar + estimate | ~4,100 | The template computes everything itself; the agent only writes `state.js` and may not touch the HTML |
| `SKILL.md` "Reading this skill" | ~1,900 | The rule is already enforced by the phase table below |
| `0-modes` "Why four and not three" + "Why this is a third dial" | ~1,400 | Design rationale addressed to a human reader, not an agent instruction |
| `SKILL.md` "The words the user sees" — rationale | ~1,100 | The table suffices |
| `rationalizations.md` | 16,941 | ~15 lines verbatim-repeat the five rules of `SKILL.md:167-171` and red flags inside the file itself; read up to three times per run |

Plus twelve point compressions (`data:`-URI forensics, the 392M/161M ceiling
arithmetic, "The reason is arithmetic, not taste", two `2-briefing` paragraphs about
the same thing) — another ≈ 3,300 tokens.

**Realistic compression ceiling: 13–18 % of startup (6–8k tokens) without losing a
single rule.** This isn't "tighten the essay" — it's striking justifications addressed
to the human reading the README out of files an agent reads in combat.

### Compaction risk

| | ~Tokens |
|---|---:|---|
| System + tools | 12,000 |
| Framework text (11 files) | 45,500 |
| Brief + manifest | 3,500 |
| `spec.md` — written by the orchestrator, so it sits entirely in its context | 15,000–25,000 |
| Tasks + `interfaces.md` | 3,500 |
| **Before the first task** | **≈ 80–90 K** |
| By phase 8 | ≈ 120 K |

T2 fits into a 200K window with ~40 % headroom. **T3 and any run with `polish` compacts
at least once**, usually between phases 5 and 8 — the framework admits this itself
(`SKILL.md:31`). `deep` shifts the compaction point to mid-build.

**Four load-bearing mechanisms live only in the context and die on compaction:**

| What is lost | Cost |
|---|---|
| Path to the skill directory (`<skill-dir>` — a placeholder, defined nowhere) | `executor.md` and `craft-review.md` stop reaching the subagents — silent code-quality degradation |
| Live reviewer handles | A new reviewer per task; cross-task findings vanish |
| Blocking finding text at follow-up time | The repair goes to waste, the `repairs` counter already spent |
| Deferred findings on tier T0 | `concerns` exists only inside the task object ([`7-instruments.md:64`](../skills/neopilot/phases/7-instruments.md#L64)); with `tickets: []` there's nowhere to put them, and phase-8 triage becomes theater |

The `state.js` skeleton is built correctly — but these four holes land exactly on the
mechanisms the framework treats as load-bearing. **Four fields at a combined cost of
~65 tokens close all four.**

## 3. Skillpack size

270 KB of text plus 79 KB of HTML that never enters the context. Of the 270 KB:

- **Mandatory core** — ~164 KB (11 startup files). Compressible by 13–18 %.
- **Conditional** — `6-review`, `9-memory` (×2), `5-repair`, `8-final`, `rationalizations`,
  `polish`. Another ~26k tokens per run.
- **Subagent material** — `executor.md`, `craft-review.md`. Compact and well
  written; leave alone except for additions from section 6.

**Little is extraneous, but much is over-explained.** The framework is written in the
genre "every rule carries its own argument" — that makes it persuasive to a human and
expensive for an agent. mattpocock formulates exactly this test: *"Hunt no-ops sentence by
sentence: an instruction the model already obeys by default pays load to say nothing.
The test — does it change behaviour versus the default? … When a sentence fails, delete
the whole sentence rather than trim words from it."* By that test, not all of our
paragraphs pass: "Read what is already here; assume nothing", "When in doubt, serialise"
(duplicates "Same files → serialise" one line above), "Order matters — the user reads the
top", "Refactoring belongs here, not inside the red-green loop".

**What's missing at a trivial price:**

1. `skillDir` in `state.js` — **~15 tokens, the most valuable edit in the audit.**
2. Top-level `concerns: []` — ~10 tokens.
3. `repairFindings: []` — finding text on disk, ~20 tokens.
4. `reviewers: {manifestSpec, craft}` — live reviewer handles, ~20 tokens.
5. An "after compaction" block in `SKILL.md`, ~120 tokens: "Lost the thread — re-read
   `state.js`, `manifest.md`, `interfaces.md`, the current phase file. Nothing else."
   Otherwise the agent re-reads `5-subagents.md` (7,730 tokens) instead of three state files.

## 4. Dashboard — 6/10

Architecture 8–9, launch procedure 4–5.

**What's done well and will survive any edit.** One truth (`state.js`), one view,
zero build step. The template is self-contained — `data:base64` logos, inline-SVG icons,
a single subresource `<script src="state.js">`. Auto-refresh is done not via reload
and not via meta-refresh but by re-fetching `state.js?t=…` every 10 s — a deliberate
workaround for panels muting navigation, and it's **measured, not assumed**. A corrupt
write is safe: `onerror`/`onload` both lead to a single `next()`, the old state stays on
screen. Re-render only on stamp change. `spanMs` returns `null` instead of `NaN`. An
explainer screen instead of blankness. For a skill this is rare maturity.

**Four high-probability failures, all silent:**

| # | Problem | Root |
|---|---|---|
| **H1** | `cp <skill-dir>/phases/dashboard-template.html` — the placeholder appears in the skill **exactly once** and is defined nowhere. Install path varies (`~/.claude/skills/`, plugin, project `.claude/skills/`). `cp` fails → no dashboard for the whole run | [`0-instruments.md:17`](../skills/neopilot/phases/0-instruments.md#L17) |
| **H2** | Not a single verification — not of `cp`, not of server liveness, not of the render. And the rule "A failure is not an error… Do not retry" effectively forbids it | [`0-instruments.md:107`](../skills/neopilot/phases/0-instruments.md#L107) |
| **H3** | The server dies silently: free port taken via bind→close (TOCTOU), stderr to `/dev/null`, `serve.pid` written unconditionally → dead PID, panel staring into nothing | [`0-instruments.md:85-87`](../skills/neopilot/phases/0-instruments.md#L85) |
| **H4** | Point Edit on non-unique anchors: `"status": "pending"` occurs 7 times in `stages`, and `updatedAt`/`startedAt`/`stages[0].startedAt` at creation time are the same string. Instructions for "what to do if the Edit didn't match" exist nowhere | [`0-instruments.md:130`](../skills/neopilot/phases/0-instruments.md#L130) |

Plus two internal contradictions: [`0-preflight.md:108`](../skills/neopilot/phases/0-preflight.md#L108)
("on resume, assume the tab is open") versus `0-instruments.md:106`; and the write
economy of [`5-subagents.md:194`](../skills/neopilot/phases/5-subagents.md#L194) ("The user
cannot see the difference — the screen follows either way") versus the `startedAt`
rule in `0-instruments.md:133` — a batched `startedAt` yields a frozen timer, exactly
what is forbidden.

And one template defect that turns a one-off failure into a permanent one: **an exception
in `render()` kills polling forever** (`applyState()` calls `render()` with no try/catch,
`pollState()` after it never runs, and `lastStamp` has already moved — a fixed
`state.js` won't re-render even manually). In a panel, navigation is muted and the user
can't reload the page.

**Six edits — about 15 lines of text and 2 lines of JS — raise the mechanism to 8–9
without changing the architecture.**

## 5. Quality loop — 6.5/10

**What's done strongly and absent from the references:**

- **Three review axes with a no-merge rule** (Manifest / Spec / Craft). mattpocock has two
  (Standards/Spec) with the same "Do not merge or rerank findings" rule; superpowers has
  one Critical/Important/Minor rubric. The Manifest axis is ours, and it "does not exist in
  ordinary code review".
- **The reviewer outlives the task.** Cross-task findings ("ticket 05 quietly contradicts
  ticket 02") are invisible to any per-ticket reviewer. No reference has this.
- **The "could the executor have known?" question** as a way to assign a finding to an
  axis — a precise and cheap classifier.
- **`interfaces.md`** as a shared contract of eight independent contexts. In superpowers
  the analogue lives in the dispatch prompt — a file is better.
- **Three "subagent" smells** (*Reinvention*, *Silent narrowing*, *Invented fact*) —
  absent from Fowler and the references alike, and they describe exactly what breaks
  in parallel work.
- **Hard ceilings**: `repairs`, `retries`, `handoffs` — all two each, with an honest
  stop on exhaustion. No infinite loop by construction.
- **Separating incompletion from failure** (same context versus fresh) with a precise
  rationale: "a cold reader repairs the symptom and breaks the reason".
- **Blind acceptance G4** with an explicit ban on opening `.neopilot/` — and the
  understanding that "not sending the file" no longer equals "hiding it" once the
  directory sits in the repository.

**What's missing:**

- **Adversarial checking of findings.** No attempt to disprove, no second opinion on a
  `clean` verdict, no protocol for reviewer disagreement.
- **The reviewer's right to execute code.** [`craft-review.md:7`](../skills/neopilot/prompts/craft-review.md#L7)
  forbids even opening a neighboring file — the central thesis "a green run is
  meaningful only if the tests could have been red" is physically unverifiable; all that
  remains is reading. superpowers has a Mutation Check for this.
- **A security axis.** No injections, no authorization, no input validation — even though
  the framework builds bots and forms with secrets.
- **Build verification.** The only one is incidental, in the memory agent: "A command that
  fails does not go in" ([`9-memory.md:106`](../skills/neopilot/phases/9-memory.md#L106)).
  A failing `npm run build` quietly stays out of the docs instead of stopping the run.
- **Running the product before phase 8.** Fifteen tasks can close on a green suite with
  the first launch happening at the very end.
- **A route for `DONE_WITH_CONCERNS`.** The status exists in the contract; no handler in
  the "After each ticket" list.

**Pressure on the reviewer points downward with no counterweight.** "Nothing to block —
write `no`, it's a normal and frequent answer" + "A reviewer that does not know this hedges
upward" — while the cost of a missed finding is never stated to them anywhere.

## 6. Developer value

Yes, substantial — and it lives in a different place than either reference's.

**What NeoPilot gives that none of them does:**

1. **A non-specialist user reaches the result.** mattpocock requires a human
   orchestrator who holds the `grill → spec → tickets → implement → review` chain by
   hand and cleans context between tickets. superpowers requires understanding which
   skill to invoke when. NeoPilot is the only one that works from a dictated brief.
2. **Observability.** For superpowers this is an admitted hole: over two hours of
   autonomous running the user sees almost nothing, controller decisions arrive as a
   single dump at the end. A dashboard with live timers is a real advantage, not a
   decoration.
3. **A requirement cannot disappear.** Manifest + four gates + blind acceptance —
   the only protection across the three frameworks against "a requirement that stopped
   existing somewhere around the third rewrite".
4. **Secrets as a cross-cutting rule** with redaction at input, before writing to a
   file. No reference has this at all.
5. **One term per stage.** "Build — the whole run", "task — unit of work".
   A UX decision nobody else has, and it's the right one.
6. **Three independent controls** (mode / depth / polish) with an honest account of why
   there are three and not one.
7. **Measurability.** `tools/measure-run.py` computes a run's real cost from logs.

**What it costs:** the most expensive start of the three (45.5k tokens versus ~15–20k
for superpowers), guaranteed compaction on T3, and a provability loop weaker than
superpowers' — while the traceability loop is stronger than both.

## 7. What not to touch

This is the list of things that must stay as-is under any edits.

1. **The verbatim-quote manifest and the four gates.** The core of the value. G2 and G4
   as "the same question at both ends of the flight" — a precise construction.
2. **Rule 5** — the orchestrator never writes code. Matches superpowers ("Never fix
   findings yourself in the controller session — your context stays clean for
   coordination, and controller fixes skip review"), and our rationale is better.
3. **Progressive disclosure by phase** and the "unit of loading is a file" rule.
4. **The ban on reading `dashboard-template.html` into context.**
5. **Executor context ceiling in tool calls + the five-line handoff**, of which three
   (`DECISIONS`, `DEADLOCKS`, `NEXT`) are the only thing not in the code.
6. **The long-lived reviewer** and the three axes with a no-merge rule.
7. **Passing material to subagents by path, not by inlining.**
8. **The three "subagent" smells** in `craft-review.md`.
9. **Secrets, `interfaces.md`, user vocabulary, modes/depth/polish.**
10. **Dashboard architecture**: one state, one view, subresource re-fetching,
    zero external dependencies.

## 9. One observation about genre

superpowers measures phrasings: the ban "don't restate the brief" produced 4.4 spec
repetitions — **worse than no instruction at all** (3.6); a positive recipe gave 3.0 with
zero variance. Hence the rule "Match the Form to the Failure": bans work against
discipline failures and backfire on output-shape failures. And the metric: "Variance is a metric.
Five different interpretations across five reps means the wording isn't binding".

Our phrasings aren't measured — they're argued. An argument persuades the human reading
the file; whether it changes agent behavior is inconsistent, and there's currently no way
to learn which paragraph works. `tools/measure-run.py` counts money and contexts — but not
rule compliance. The strongest investment on the horizon after edits 1–8: **five runs of
the same brief, recording where the instruction failed to fire, and rewriting exactly
those phrasings.** Then section 8 in the next audit will rest on measurement, not reading.
